1. PROJECT OVERVIEW
-------------------

Ledgerly Business Finance is a full-stack business finance application.

It allows users to:

- Register and log in securely.
- Record income and expense transactions.
- Edit and delete transactions.
- Organize transactions with categories.
- Create monthly category budgets.
- Set monthly income and savings targets.
- Compare planned budgets with actual transaction spending.
- View monthly dashboard analytics.
- Track budget progress and identify over-budget categories.
- See upcoming bills and calculate available spending money.
- Filter, sort, and paginate transaction records.

The application is designed as a desktop-focused financial dashboard with an ANB-inspired teal banking theme, white panels, structured tables, summary cards, progress bars, and status badges.

3. APPLICATION ARCHITECTURE
---------------------------

The project uses a layered architecture:

    React UI
        |
        v
    Client service
        |
        v
    Client repository / HTTP access
        |
        v
    Express REST API
        |
        v
    Controller
        |
        v
    Server service
        |
        v
    Server repository
        |
        v
    Prisma ORM
        |
        v
    PostgreSQL database

Responsibilities:

UI:
- Displays forms, tables, dashboards, buttons, loading states, and errors.
- Collects user input.
- Stores temporary screen state.
- Calls client services when a user performs an action.

Services:
- Contain business rules and calculations.
- Validate data.
- Check ownership and permissions.
- Coordinate repositories.
- Calculate financial values such as income, expenses, remaining money, and budget status.

Repositories:
- Handle data access.
- The client HTTP repository sends requests to the API.
- Server repositories contain Prisma queries.
- Repositories should not decide what the user is allowed to do or how the UI looks.

Controllers:
- Translate HTTP requests into service calls.
- Send service results as HTTP responses.
- Pass errors to the central error handler.

Routes:
- Connect URL paths and HTTP methods to controllers.
- Apply authentication middleware to protected endpoints.

Database:
- Permanently stores application data in PostgreSQL.
- Prisma schema and migrations describe the database structure.

4. HOW A REQUEST WORKS
----------------------

Example: creating a transaction.

1. The user fills out the transaction form in the React UI.
2. TransactionsPage.handleSubmit collects amount, type, category, description, and date.
3. The client apiService is called.
4. httpRepository sends a POST request to /api/transactions.
5. Express matches the request to transactionRoutes.js.
6. authMiddleware verifies the JWT and identifies the current user.
7. transactionController.create receives the HTTP request.
8. transactionService.createTransaction validates the data and checks category ownership.
9. transactionRepository.createTransaction sends the database operation to Prisma.
10. PostgreSQL stores the transaction.
11. The saved row travels back through the repository, service, and controller.
12. The browser receives the response.
13. The React page reloads the list and displays the new transaction row.

The UI does not directly query PostgreSQL. The service decides what should happen, and the repository decides how data is stored.

7. REST API ENDPOINTS
---------------------

Health:

GET /api/health
- Returns a simple status response.
- Does not require authentication.

Authentication:

POST /api/auth/register
- Creates a user account.
- Input includes email and password.

POST /api/auth/login
- Checks credentials and returns a JWT and user information.

POST /api/auth/logout
- Returns a logout confirmation.
- The browser removes the stored token.

GET /api/auth/me
- Returns the current authenticated user.
- Requires a valid JWT.

Transactions:

GET /api/transactions
- Lists the authenticated user's transactions.
- Supports pagination, filtering, date ranges, category, type, sorting, and sort direction.

GET /api/transactions/:id
- Retrieves one transaction owned by the current user.

POST /api/transactions
- Creates a transaction.

PATCH /api/transactions/:id
- Updates a transaction owned by the current user.

DELETE /api/transactions/:id
- Deletes a transaction owned by the current user.

Categories:

GET /api/categories
- Lists the current user's categories.

POST /api/categories
- Creates a category.

PATCH /api/categories/:id
- Updates a category owned by the current user.

DELETE /api/categories/:id
- Deletes a category when it has no linked transactions.

Budgets:

GET /api/budgets
- Lists category budget rows.

POST /api/budgets
- Creates a category budget for a month and year.

PATCH /api/budgets/:id
- Updates a category budget.

DELETE /api/budgets/:id
- Deletes a category budget.

GET /api/budgets/planner?year=YYYY&month=MM
- Returns the monthly planner view model.
- Includes targets, actual income, expenses, category spending, statuses, unassigned money, and upcoming bills.

PUT /api/budgets/monthly
- Saves monthly income and savings targets.

Analytics:

GET /api/analytics/monthly?year=YYYY&month=MM
- Returns monthly income, expenses, net balance, spending by category, and budget status.

All endpoints except health and registration/login require authentication where indicated by the route configuration.

User:

Category:

- id: Unique category identifier.
- userId: Owner of the category.
- name: Category name.
- type: INCOME or EXPENSE.
- Relationships to transactions and budgets.
- User/category name is unique.

Transaction:

- id: Unique transaction identifier.
- userId: Owner of the transaction.
- categoryId: Related category.
- amount: Decimal financial amount.
- type: INCOME or EXPENSE.
- description: Human-readable explanation.
- transactionDate: Date the transaction occurred.
- User and category relationships.

Budget:

- id: Unique budget identifier.
- userId: Owner.
- categoryId: Planned spending category.
- month and year: Budget period.
- amount: Planned amount.
- One category budget is allowed per user/category/month/year combination.

MonthlyBudget:

- id: Unique monthly target identifier.
- userId: Owner.
- month and year: Target period.
- incomeTarget: Planned monthly income.
- savingsTarget: Planned monthly savings.
- One monthly target row is allowed per user/month/year combination.

TransactionType:

- INCOME
- EXPENSE

Important design decision:

Budgets do not store a duplicated spent amount. Actual spending is calculated from transactions. This means creating, editing, or deleting a transaction automatically changes budget tracking the next time the planner loads.

9. FINANCIAL CALCULATIONS
-------------------------

Monthly income:

    totalIncome = sum of transactions where type is INCOME

Monthly expenses:

    totalExpenses = sum of transactions where type is EXPENSE

Current balance:

    currentBalance = totalIncome - totalExpenses

Remaining money:

    remaining = totalIncome - totalExpenses - savingsTarget

Assigned money:

    totalAssigned = category budget amounts + savings target

Unassigned money:

    unassigned = income target - totalAssigned

Available spending:

    availableToSpend = current balance - upcoming bills

Budget remaining:

    remaining category budget = planned category budget - actual category spending

Budget percentage:

    percentageUsed = actual spending / planned budget * 100

Budget statuses:

- 0 through 79 percent: On Track.
- 80 through 99 percent: Near Limit.
- 100 percent or greater: Over Budget.

The progress bar is visually limited to 100 percent, but the text can still show a value above 100 percent so overspending is not hidden.

Monthly ranges use UTC calendar boundaries. This keeps a transaction on the first day of a month in the correct month even when server and database time zones differ.

10. SECURITY AND VALIDATION
---------------------------

- Passwords are hashed with bcryptjs instead of being stored as plain text.
- JWT tokens are verified by authentication middleware.
- Protected records include user ownership checks.
- Categories must belong to the current user before they are attached to transactions or budgets.
- Amounts must be greater than zero for transaction and category-budget creation.
- Email format is validated during authentication.
- Passwords must meet the minimum length rule.
- Transaction type must be INCOME or EXPENSE.
- Category type must be INCOME or EXPENSE.
- Express error middleware returns friendly API errors without exposing unexpected implementation details.
- Helmet adds common HTTP security headers.
- CORS uses the configured client origin.

11. DESIGN PATTERNS AND PRINCIPLES
----------------------------------

Layered Architecture:

The most important pattern is layered architecture. Each layer has a focused job and calls the next layer instead of bypassing it.

Repository Pattern:

Repositories hide database and HTTP storage details. Services ask repositories for data without needing to know the exact Prisma query or fetch setup.

Service Layer Pattern:

Services contain application rules such as validation, ownership checks, calculations, and coordination of multiple repositories.

Controller Pattern:

Controllers adapt HTTP requests and responses to service functions. They remain intentionally thin.

Middleware Pattern:

Express middleware runs during the request pipeline. Authentication middleware verifies tokens before protected controllers run. Error middleware handles failures consistently.

Component-Based UI:

React pages and reusable components such as SummaryCard and Panel split the interface into smaller pieces.

Single Responsibility Principle:

The project attempts to keep UI, services, repositories, controllers, and database access focused on different responsibilities.

REST-style API:

The backend uses HTTP verbs and resource URLs:

- GET reads data.
- POST creates data.
- PATCH updates part of an existing record.
- DELETE removes data.

16. SHORT SUMMARY
-----------------

Ledgerly Business Finance is a React and Node.js business finance dashboard backed by PostgreSQL. React provides the user interface, Express provides the REST API, Prisma connects the server to PostgreSQL, and JWT plus bcryptjs handle authentication.

The application supports authentication, transactions, categories, monthly budgets, analytics, budget progress, upcoming bills, pagination, filtering, sorting, and ownership protection.

Its main design pattern is layered architecture with services and repositories. The code separates display logic, business rules, data access, and persistent storage so the project can be understood and extended one layer at a time.
